# Real open-weight Qwen extraction smoke run — 2026-07-14

## Purpose

This run tested whether the concrete OpenAI-compatible backend in PR #31 can execute a real
open-weight model and return molecular-dynamics metadata. It was an operational and failure-mode
study, not a corpus accuracy benchmark.

The available GitHub-hosted runner had no GPU. It could not load the default
`Qwen/Qwen3.6-27B`, so the experiment used the smaller open-weight
`Qwen/Qwen3.5-0.8B` model in Q8_0 GGUF form. Results from this model must not be presented as
Qwen3.6-27B results.

## Locked environment

- runner: GitHub-hosted `ubuntu-24.04`, CPU only;
- inference server: official `llama.cpp` binary installed from `https://llama.app/install.sh`;
- weight source: `ggerganov/Qwen3.5-0.8B-GGUF:Q8_0`;
- served model alias: `Qwen/Qwen3.5-0.8B`;
- server: loopback OpenAI-compatible endpoint, one parallel request, four inference threads;
- context length: 8,192 tokens;
- decoding: temperature 0, top-p 1, seed 0, thinking disabled;
- source paragraph:

  > The production simulation was run for 100 ns at 300 K and 1 bar in the NPT ensemble with a
  > 2 fs time step using three replicates.

No API-hosted proprietary model was used, and no mocked model response was used in the runs below.

## Experiment sequence

### 1. Full repository JSON Schema, four cases

The first bounded run used the repository's complete nested event schema and exact-span validator.
It tested a complete production event, a sampling-interval/time-step distinction, a non-MD negative
paragraph, and a thermostat-coupling-time trap.

With a 45-second request limit:

- the negative paragraph completed correctly with `{"events": []}`;
- the negative request used 289 input tokens and 15 output tokens;
- observed negative latency was approximately 37–42 seconds across repeated runs;
- the three positive requests timed out before returning an HTTP response;
- the validator accepted one of four cases, solely because the completed negative control was
  correct.

The resulting `0.25` strict-case fraction is not an accuracy estimate: three cases were operational
timeouts rather than incorrect completed predictions.

Representative workflow run: `29371999929`.

### 2. Full positive event with a 180-second request limit

The complete production paragraph was run alone with the full nested schema. It again timed out
without a response after 180 seconds.

Representative workflow run: `29372541109`.

### 3. Compact evidence-first JSON Schema

A smaller schema asked only for one event, one quote, and raw strings for duration, temperature,
pressure, time step, ensemble, and replicate count. It removed nested quantity objects and left all
numeric conversion to deterministic code.

The request still timed out after 180 seconds. This showed that nested Pydantic structure was not the
only bottleneck; positive grammar-constrained generation itself was not practical in this CPU setup.

Representative workflow run: `29373111626`.

### 4. Unconstrained long JSON control

The same model and paragraph were then queried without `response_format=json_schema`. The prompt
still requested a full quote and all metadata fields as ordinary JSON. It also timed out after about
180.2 seconds.

This indicated that the dominant limit was CPU generation throughput for a longer positive answer,
not only JSON Schema grammar compilation.

Representative workflow run: `29373383199`.

### 5. Minimal positive capability control

The final control reduced the target to six short fields and at most 80 output tokens. This request
completed successfully:

```json
{
  "duration": "100 ns",
  "temperature": "300 K",
  "pressure": "1 bar",
  "timestep": "2 fs",
  "ensemble": "NPT",
  "replicates": "3"
}
```

Observed result:

- latency: approximately 141.8–142.1 seconds;
- prompt tokens: 76;
- completion tokens: 64;
- total tokens: 140;
- duration: exact;
- temperature: exact;
- pressure: exact;
- time step: exact;
- ensemble: exact;
- replicate count: semantically correct but not an exact source copy (`"3"` instead of
  source text `"three"`).

The strict field-copy check therefore failed five-of-six-versus-six-of-six, even though the model
identified all six underlying values. This is an important scientific result: a language model may
silently normalise evidence while preserving meaning. The repository's exact-source checks are
therefore necessary rather than cosmetic.

Representative workflow run: `29373642112`.

## Interpretation

### What was demonstrated

1. A real open-weight Qwen model was downloaded, loaded and served through a local
   OpenAI-compatible endpoint.
2. PR #31's client reached that endpoint successfully.
3. The model correctly abstained on a non-MD negative paragraph.
4. In a minimal positive request, it identified duration, temperature, pressure, integration time
   step, ensemble and replicate count.
5. The experiment exposed an exact-evidence error: `three` was normalised to `3`.
6. The audit and deterministic validation design prevented that semantically plausible change from
   being misreported as exact evidence.

### What was not demonstrated

- Qwen3.6-27B performance;
- GPU inference performance;
- full-schema positive extraction within an operationally acceptable latency;
- accuracy on the 60-article corpus;
- superiority over the deterministic extractor;
- DeepSeek performance;
- a human-reference precision, recall or F1 result.

## Decision

`Qwen3.5-0.8B` Q8 on a GitHub CPU runner is not a viable production backend for this task. Even the
minimal 64-token positive completion required about 142 seconds, while longer positive outputs
exceeded 180 seconds.

The next scientifically meaningful run should use a GPU-backed vLLM or SGLang server with an exact
model revision, beginning with `Qwen/Qwen3.6-27B` if hardware permits. The same source paragraphs,
prompt version, schema, seed, code commit and validation rules should be frozen. The run should then
compare deterministic-only, LLM-only and hybrid predictions against independent human dual
annotation and adjudication.

The production acceptance rule remains unchanged: model output is a candidate only. Exact source
spans, raw expressions and deterministic parsing must pass before a record is accepted.
