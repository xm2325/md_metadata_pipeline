# Live PDBe-KB/FunPDBe integration run — 2026-07-15

## Purpose

Validate the repository's direct PDBe-KB/FunPDBe integration against real service responses rather
than mocked payloads. The run tested provider discovery, provider-specific annotation retrieval,
residue-level projection, response hashing and explicit conflict semantics.

This is an integration smoke result for two structures, not a coverage estimate for all PDB entries
or all PDBe-KB providers.

## Discovery result

The catalogue endpoint returned four provider records for each structure. Catalogue records contained
provider metadata such as `origin`, `labels`, `evidence_codes`, `release_date` and `url`; residue
annotations were not embedded in those catalogue rows. The adapter was therefore corrected from a
one-stage parser to a two-stage process:

1. fetch the provider catalogue for the PDB entry;
2. call the provider-specific annotation endpoint for each discovered origin;
3. project explicit site residues and scores;
4. retain a provider-level status and response digest;
5. keep network/format failures distinct from a successful no-data response.

## Projected common contract

The adapter projects only explicitly supplied common fields:

- provider and label/type;
- chain identifier;
- PDBe residue number/range;
- author residue number and insertion code when present;
- entity identifier;
- raw score;
- confidence score and classification;
- source-record SHA-256.

Unknown provider-specific fields are not inferred. The full provider response can be retained for a
controlled profiling run, while normal runs retain the compact projection and request provenance.

## Verification policy

The two-stage parser and state semantics are covered by mocked regression tests for successful site
projection, valid empty responses, explicit provider 404 conflicts, malformed payloads, network
failure and invalid PDB identifiers. The code-bearing head passed the Python 3.11/3.12 test matrix,
Ruff and security gates before the final documentation-only commits. The external live workflow is
now manual-only to avoid repeatedly retrieving tens of thousands of annotations on ordinary pushes.

## Interpretation

### Demonstrated

1. Direct live integration with the PDBe Graph API.
2. Discovery of the real two-stage FunPDBe API contract.
3. Residue-level projection from three provider families.
4. Explicit representation of a provider catalogue/annotation conflict.
5. Response hashing, request history and fail-closed malformed/network handling.
6. A practical reason to keep PDBe-KB as a versioned sidecar before migrating tens of thousands of
   heterogeneous annotation rows into the stable IntegratedMDRecord and public API.

### Not demonstrated

- complete provider coverage across the PDB;
- stable longitudinal behaviour under upstream schema changes;
- direct loading of all 41,600 rows into the authoritative SQLite release schema;
- biological validation of every provider score;
- an official PDBe-KB or SIFTS contribution;
- overlap analysis between these annotations and the project's MD-residue mappings.

## Decision

Retain the two-stage PDBe-KB result as an audited sidecar for the current version. Before changing the
stable release/API contract:

1. profile a stratified sample of structures and providers;
2. quantify row counts, missingness and field variability;
3. agree which controlled fields are useful with structural-biology users;
4. define indexes and pagination for residue annotations;
5. test overlap with MD→PDB→UniProt correspondences;
6. migrate through a versioned schema change rather than inserting provider-specific blobs directly.
